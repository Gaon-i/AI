제목 : [regulation_chunk 벌크 적재/N+1 성능 문제] 프로젝트 - 1
1. 문제 개요
오류 상황: 벌크 적재 API가 각 청크마다 DB 중복 조회와 OpenAI 임베딩 호출을 개별 수행해 요청 수가 늘수록 성능이 급격히 저하되는 구조였습니다.
발생 배경: 코드 리뷰에서 20건 벌크 적재 시 DB 쿼리와 외부 API 호출이 각각 20번씩 발생하는 N+1 문제가 지적되었습니다.
2. 오류 코드 및 오류 메시지
오류 코드: 명시적인 HTTP 오류는 아니지만, 응답 지연과 외부 API 호출 수 증가가 문제였습니다.
오류 메시지: 별도 메시지 없음
관련 로그: 벌크 생성 로직에서 `find_by_chunk_id()`와 `create_embedding()`이 반복 호출되는 구조가 확인되었습니다.
3. 원인 분석
오류 원인: 벌크 적재 로직이 단건 생성 내부 함수를 그대로 반복 호출하면서 DB 조회와 임베딩 생성을 배치 처리하지 못했습니다.
에러 로그 해석: 직접적인 에러 로그보다 서비스 코드 구조를 분석했을 때 N+1 패턴이 명확히 드러났습니다.
구조적 이해: OpenAI Embeddings API는 문자열 배열 입력을 지원하고, SQLAlchemy도 `IN` 쿼리로 여러 키를 한 번에 조회할 수 있어 벌크 적재 최적화가 가능합니다.
4. 해결책
단계별 조치 방법:
Step 1: repository에 `find_existing_chunk_ids()`를 추가해 chunk_id 중복 여부를 한 번의 쿼리로 조회했습니다.
Step 2: embedding service에 `create_embeddings_batch()`를 추가해 여러 chunk_text를 한 번의 OpenAI 호출로 처리했습니다.
Step 3: bulk service가 중복 체크, chunk_text 생성, 배치 임베딩 생성, DB 저장을 각각 한 번씩만 수행하도록 리팩터링했습니다.
코드 예시:
```python
existing_chunk_ids = find_existing_chunk_ids(db, chunk_ids)
embeddings = create_embeddings_batch(chunk_texts)
```
추가 자료: https://platform.openai.com/docs/api-reference/embeddings/create
5. 교훈 및 주의 사항
주의할 점: 단건 생성 함수를 단순 반복 호출하면 bulk 처리에서 쉽게 N+1 문제가 생깁니다.
배운 점: bulk API는 처음부터 배치 DB 조회와 배치 외부 호출 구조를 염두에 두고 설계해야 성능 문제를 예방할 수 있습니다.

Step 3: `pip install -e ".[dev]"`로 프로젝트 의존성을 다시 설치했습니다.
Step 4: 개발 문서의 Quick Start도 `python -m pip install --upgrade pip` 후 설치하도록 수정했습니다.
코드 예시:
```bash
python -m pip install --upgrade pip
pip install -e ".[dev]"
```
추가 자료: https://pip.pypa.io/en/stable/topics/local-project-installs/
5. 교훈 및 주의 사항
주의할 점: `pyproject.toml`을 쓰는 프로젝트는 의존성만 맞다고 끝나는 것이 아니라, 가상환경의 `pip` 버전도 함께 관리해야 합니다.

1. 문제 개요
오류 상황: 공지 목록 크롤링은 성공했지만, 상세 페이지 본문 수집 단계에서 `HTTPStatusError`로 동기화 배치가 중단되었습니다.
발생 배경: `python -m app.jobs.notice_sync`로 실제 학생생활관 공지 크롤링을 처음 실행했을 때 목록 페이지는 열렸지만 상세 페이지 요청이 실패했습니다.
2. 오류 코드 및 오류 메시지
오류 코드: `302 Moved Temporarily`
오류 메시지: `httpx.HTTPStatusError: Redirect response '302 Moved Temporarily'`
관련 로그: `https://www.gachon.ac.kr/bbs/dormitory/330/.../artclView.do` 요청 시 `https://www.gachon.ac.kr/dormitory/2351/subview.do?enc=...`로 리다이렉트되는 응답이 확인되었습니다.
3. 원인 분석
오류 원인: 가천대 공지 상세 페이지는 직접 `artclView.do`를 여는 것이 아니라, 실제로는 `subview.do?enc=...` 경로로 302 리다이렉트되는 구조였습니다. 그런데 크롤러의 `httpx.Client.get()` 호출이 redirect follow 옵션 없이 작성되어 있었습니다.
에러 로그 해석: DNS나 인증 문제가 아니라, 서버가 정상적으로 302 응답을 주고 있었기 때문에 네트워크 연결은 성공했지만 HTTP 흐름 처리가 불완전한 상태였습니다.
구조적 이해: 게시판 시스템은 내부적으로 직접 상세 URL 대신 인코딩된 `subview.do` 경로를 사용하는 경우가 많아, 크롤러는 redirect를 정상 흐름으로 처리해야 합니다.
4. 해결책
단계별 조치 방법:
Step 1: 공지 크롤러의 `fetch_html()`에서 `client.get(url, follow_redirects=True)`로 수정했습니다.
Step 2: 수정 후 `python -m app.jobs.notice_sync`를 다시 실행해 실제 공지 1건이 크롤링, 저장, 요약되는지 확인했습니다.
코드 예시:
```python
response = client.get(url, follow_redirects=True)
```
추가 자료: https://www.python-httpx.org/quickstart/#redirection-and-history
5. 교훈 및 주의 사항
주의할 점: 웹 크롤링에서 상세 링크가 보인다고 해서 그 URL이 최종 응답 페이지라는 보장은 없습니다.
배운 점: 실제 사이트를 처음 붙일 때는 목록 파싱 테스트 외에도 한 번은 네트워크를 열어 실사이트 redirect/인코딩 흐름을 확인해야 합니다.

오류 메시지: 별도 메시지 없음

- `800` 글자 제한 하드코딩
- 긴 단일 문단이 제한 초과여도 그대로 한 청크로 남는 구조
3. 원인 분석
오류 원인: 초기 구현 단계에서 “일단 동작하는 구조”를 우선 만들면서, 시간 유틸 통일·DB 집계 최적화·검색용 청크 포맷 일관성·설정 분리 같은 운영성 요소가 뒤로 밀렸습니다.
에러 로그 해석: 런타임 예외가 아니라, 코드 리뷰를 통해 드러난 잠재 품질 문제였습니다. 트래픽 증가나 문서 다양화가 진행되면 성능/검색 품질 저하로 이어질 가능성이 있었습니다.
구조적 이해:
- 시간 API는 Python 버전 변화까지 고려해 미래 호환성을 챙겨야 합니다.

제목 : [chat 저장 로직/불필요한 refresh와 실패 시 retrieval 근거 보존 문제] 프로젝트 - 13
1. 문제 개요
오류 상황: 채팅 관련 repository에서 `db.flush()` 직후 `db.refresh()`를 반복 호출해 불필요한 SELECT가 발생하고 있었고, 동시에 답변 생성 실패 시에도 검색 근거를 관리자 화면에서 볼 수 있어야 한다는 요구가 함께 제기되었습니다.
발생 배경: PR 리뷰에서 `chat_retrieval_result` 저장/업데이트 루프와 `touch_chat_session_activity()`에 있는 `refresh()` 호출, 그리고 “LLM 실패 시 retrieval 결과가 롤백으로 사라지지 않는가”에 대한 피드백이 들어왔습니다.
2. 오류 코드 및 오류 메시지
오류 코드: 즉시 드러나는 HTTP 오류는 없었음
오류 메시지: 별도 메시지 없음
관련 로그:
- `create_chat_retrieval_results()`에서 row마다 `db.refresh(retrieval_result)` 수행
- `mark_chat_retrieval_results_used_in_answer()`에서 row마다 `db.refresh(retrieval_result)` 수행
- `touch_chat_session_activity()`에서 `db.refresh(chat_session)` 수행
- 채팅 처리 중 LLM 호출 실패 시 검색 근거 row 보존 여부 검토 필요
3. 원인 분석
오류 원인: flush 이후 객체 상태를 과도하게 즉시 재조회하는 패턴이 남아 있었고, 실패 경로에서 어떤 데이터까지 “관측 가능해야 하는지”에 대한 정책이 코드 구조에 충분히 드러나지 않았습니다.
에러 로그 해석: 에러라기보다 성능과 운영 관측성 관점의 구조 개선 포인트였습니다. `refresh()` 루프는 작은 데이터에서는 티가 덜 나지만, row 수가 늘면 N+1 SELECT로 이어질 수 있습니다.
구조적 이해:
- SQLAlchemy는 `flush()`만으로도 INSERT된 PK와 세션 내부 변경 상태를 객체에 반영합니다.
- DB trigger 등으로 DB 쪽에서 값이 바뀌는 경우가 아니라면 직후 `refresh()`가 꼭 필요하지 않습니다.
- retrieval 결과는 “답변 생성 전 검색 근거”이므로, LLM 실패가 나더라도 관리자 추적을 위해 남겨두는 편이 운영상 유리합니다.
4. 해결책
단계별 조치 방법:
Step 1: `chat_retrieval_result` 생성/업데이트 후 반복 `refresh()`를 제거했습니다.
Step 2: `touch_chat_session_activity()`의 불필요한 `refresh()`를 제거했습니다.
Step 3: 채팅 처리 구조를 retrieval 저장까지 먼저 commit하고, 이후 LLM 호출과 최종 상태 저장을 분리해 retrieval 근거가 실패 시에도 보존되도록 유지했습니다.
코드 예시:
```python
db.flush()
return created_items
```
```python
db.commit()
db.close()

answer_result = generate_answer(question, labeled_chunks)
```
추가 자료:
- https://docs.sqlalchemy.org/en/20/orm/session_basics.html
- https://docs.sqlalchemy.org/en/20/orm/session_state_management.html
5. 교훈 및 주의 사항
주의할 점: `refresh()`는 “안전해 보이는 기본 동작”처럼 느껴지지만, 실제로는 쿼리 수를 늘리는 비용이 있으므로 필요한 경우에만 써야 합니다.
배운 점: 운영 추적이 중요한 시스템에서는 “최종 답변 성공 여부”뿐 아니라 “실패 직전까지 확보한 근거 데이터도 남길 것인가”를 의식적으로 설계해야 합니다.
