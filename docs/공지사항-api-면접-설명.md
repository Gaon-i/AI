# 공지사항 수집·요약 API 면접 설명 문서

## 1. 한 문장 소개

이 기능은 가천대학교 학생생활관 공지사항을 매일 수집하고, 최근 30일 공지만 유지하면서, LLM으로 핵심 요약을 생성해 API로 제공하는 백엔드 시스템입니다.

## 2. 왜 만들었는가

학생들은 기숙사 공지 원문이 길고 양식이 일정하지 않아 필요한 정보를 빠르게 파악하기 어렵습니다.  
그래서 다음 문제를 해결하고자 했습니다.

- 최근 공지를 자동 수집하고 누락 없이 적재하기
- 원문 전체를 읽지 않아도 핵심 요약을 빠르게 볼 수 있게 하기
- 이번 주/이번 달 공지 수까지 함께 제공해 공지량을 직관적으로 보여주기
- 오래된 공지는 자동 정리해서 데이터 최신성을 유지하기

## 3. 요구사항을 어떻게 분해했는가

이 기능은 단순 API 하나가 아니라 4개 하위 문제로 쪼개서 설계했습니다.

1. 크롤링
- 학생생활관 공지 목록 페이지에서 최근 공지를 가져온다.
- 각 공지 상세 페이지에 들어가 원문 본문을 추출한다.

2. 저장
- 원문 공지는 `notice` 테이블에 저장한다.
- 요약 결과는 `notice_summary` 테이블에 분리 저장한다.

3. 배치
- 매일 12시에 자동 실행할 수 있도록 수동 실행 가능한 sync job을 만든다.
- 최근 30일이 지난 공지는 자동 삭제한다.

4. 조회 API
- 단건 요약 API
- 공지 목록 API

## 4. 전체 아키텍처

흐름은 아래와 같습니다.

1. `app.jobs.notice_sync` 실행
2. `notice_crawler`가 목록/상세 페이지를 파싱
3. `notice_sync_service`가 공지 원문을 `notice`에 upsert
4. 구조화 요약을 생성해 `notice_summary`에 upsert
5. 30일이 지난 데이터는 삭제
6. `GET /api/v1/notices`가 최근 공지 목록과 집계를 반환

## 5. 테이블을 2개로 나눈 이유

### `notice`

원문 저장소 역할입니다.

- `title`
- `content`
- `source_url`
- `posted_at`
- `collected_at`

### `notice_summary`

파생 데이터 저장소 역할입니다.

- `summary_text`
- `target_info`
- `schedule_info`
- `caution_info`
- `generated_model`
- `generated_at`

### 이렇게 분리한 이유

- 원문과 요약의 책임을 분리할 수 있습니다.
- 요약 모델이나 프롬프트가 바뀌어도 원문을 기준으로 재생성할 수 있습니다.
- 크롤링 원문을 근거 데이터로 보관할 수 있습니다.
- 향후 검색, 재요약, 분류 기능 확장이 쉬워집니다.

## 6. 핵심 API 설명

### 1. 단건 요약 API

`POST /api/v1/ai/notice_summary`

입력:
- `title`
- `content`

출력:
- `title`
- `summary`
- `target_info`
- `schedule_info`
- `caution_info`

이 API는 크롤링 저장용이라기보다 요약 기능 검증과 단건 테스트용 성격이 강합니다.

### 2. 공지 목록 API

`GET /api/v1/notices`

출력:
- `weekly_count`
- `monthly_count`
- `items`

각 item:
- `notice_id`
- `title`
- `source_url`
- `posted_at`
- `summary`
- `target_info`
- `schedule_info`
- `caution_info`

여기서 원문 `content`는 DB에는 저장하지만 API DTO에서는 제외했습니다.  
이유는 목록 응답을 가볍게 유지하고, 프론트에서는 요약 중심으로 보여주기 위함입니다.

## 7. 크롤러를 어떻게 구현했는가

초기 구현은 Selenium이 아니라 `httpx + BeautifulSoup`로 시작했습니다.

이유:
- 현재 대상 사이트는 서버 렌더링 HTML에서 목록/본문이 파싱 가능했습니다.
- 로그인, 무한스크롤, 동적 렌더링 의존이 없어 더 가볍고 유지보수가 쉬웠습니다.
- Selenium은 운영 비용과 실패 지점이 더 많아서 fallback으로 남겨두는 것이 낫다고 판단했습니다.

### 목록 페이지

- `subview.do` 게시판 목록을 읽습니다.
- `article.offset`, `articleLimit` 쿼리로 페이지를 넘깁니다.
- 공지 링크와 등록일을 추출합니다.

### 상세 페이지

- 직접 상세 URL을 호출하면 실제로는 `subview.do?enc=...`로 302 redirect 됩니다.
- 그래서 `follow_redirects=True`로 처리했습니다.
- 본문은 `등록일` 이후부터 `첨부파일` 전까지를 본문으로 간주해 추출했습니다.

## 8. 왜 최근 30일 기준으로 설계했는가

요구사항은 “최근 1개월”이었지만, 구현 기준은 최근 30일로 고정했습니다.

이유:
- 달(month) 기준보다 계산이 단순하고 예측 가능합니다.
- 테스트 작성이 명확합니다.
- 운영 시각 차이 때문에 경계값이 흔들리는 문제를 줄일 수 있습니다.

삭제 정책:
- `notice_summary` 먼저 삭제
- `notice` 이후 삭제

이 순서를 택한 이유는 FK 제약 때문입니다.

## 9. KST 기준으로 맞춘 이유

배치는 클라우드 서버에서 돌릴 예정이기 때문에 서버 로컬 시간에 의존하면 UTC 환경에서 기준이 흔들릴 수 있습니다.  
그래서 API 조회와 batch sync 기준 시각은 KST 기준 naive datetime으로 맞췄습니다.

면접에서 이렇게 설명하면 됩니다.

> “로컬 개발에선 큰 차이가 없지만, 운영 서버가 UTC로 떠 있으면 주간/월간 집계와 30일 cutoff가 틀어질 수 있어서, 비즈니스 기준 시간대를 KST로 고정했습니다.”

## 10. 비용과 중복 호출 문제는 어떻게 막았는가

매일 배치를 돌리면 최근 30일 공지를 계속 다시 읽게 됩니다.  
처음 구현에서는 같은 공지를 매일 다시 요약할 위험이 있었고, 이건 OpenAI 비용과 지연 시간 모두에 불리합니다.

그래서 sync 단계에서 아래 조건을 넣었습니다.

- 같은 `source_url` 공지가 이미 있고
- `title`, `content`, `posted_at`이 바뀌지 않았고
- 기존 summary도 있으면

재요약을 건너뜁니다.

이렇게 해서 배치를 다시 돌려도 불필요한 LLM 호출을 막았습니다.

## 11. 에러 처리 관점

이번 구현에서 신경 쓴 실패 지점은 3개입니다.

1. 크롤링 실패
- 네트워크 오류
- 대상 사이트 redirect 구조
- HTML 구조 변경

2. DB 저장 실패
- upsert 과정 예외
- 삭제 과정 예외

3. 요약 실패
- OpenAI 호출 실패
- 구조화 JSON 파싱 실패 가능성

현재 구조는 실패가 나면 예외를 올려서 batch가 실패하도록 했고, 이후 운영 단계에서 로그/알림 강화가 가능한 형태로 남겨뒀습니다.

## 12. 테스트 전략

이 기능은 외부 의존성이 많기 때문에 테스트를 계층별로 나눴습니다.

### 파서 테스트
- 목록 HTML에서 제목/등록일/링크를 제대로 뽑는지
- 상세 HTML에서 메타데이터/첨부파일 영역을 제외한 본문만 추출하는지

### 서비스 테스트
- notice upsert
- summary upsert
- 최근 공지 조회
- 만료 공지 삭제

### sync 테스트
- crawl -> save -> summarize -> delete 연결
- 구조화 요약 필드 전달
- 변경 없는 공지 재요약 skip

### API 테스트
- 단건 요약 API 응답 구조
- 목록 조회 API 응답 구조

## 13. 실제로 겪었던 문제와 해결

면접에서 강조하면 좋은 실제 이슈는 아래입니다.

1. `openai` 의존성이 `pyproject.toml`에 빠져 있어서 서버가 import 단계에서 죽었던 문제
2. `pip`가 오래되어 editable install이 실패한 문제
3. 상세 페이지 302 redirect 미처리
4. 모델과 Alembic 스키마 drift
5. `generated_at`에 SQL expression이 남아 API 직렬화에 위험했던 문제
6. 테스트 환경에서 OpenAI client가 import 시점에 먼저 생성되어 깨지던 문제
7. 최근 30일 공지를 매일 다시 요약하는 비용 문제
8. KST가 아닌 서버 시간에 의존하면 집계 기준이 틀어지는 문제

이런 포인트는 단순 CRUD가 아니라 운영까지 생각했다는 인상을 줍니다.

## 14. 면접에서 이렇게 설명하면 좋다

짧은 버전:

> “학생생활관 공지를 매일 자동 수집해서 최근 30일 데이터만 유지하고, 원문은 `notice`, 요약은 `notice_summary`에 분리 저장했습니다. 크롤링은 `httpx + BeautifulSoup`, 요약은 OpenAI 구조화 응답으로 구현했고, `GET /api/v1/notices`에서 주간/월간 건수와 요약 목록을 제공하도록 만들었습니다. 운영 기준 시간대는 KST로 맞추고, 동일 공지 재요약은 건너뛰도록 해서 비용과 데이터 일관성을 함께 고려했습니다.”

조금 더 긴 버전:

> “이 기능은 단순 API보다 배치 파이프라인에 가까웠습니다. 먼저 공지 목록/상세 크롤러를 만들고, 원문 보관용 `notice`와 요약 저장용 `notice_summary`를 분리했습니다. 이후 매일 실행 가능한 sync job을 만들고, 최근 30일 이내 공지만 유지하도록 삭제 정책까지 넣었습니다. 요약은 단순 문자열이 아니라 `summary`, `target_info`, `schedule_info`, `caution_info` 구조로 저장해서 이후 프론트 표시와 확장성을 높였습니다. 또한 같은 공지를 매일 재요약하지 않도록 idempotency를 고려했고, 운영 서버 시간대가 달라도 결과가 흔들리지 않도록 KST 기준 시각을 고정했습니다.”

## 15. 예상 질문과 답변 포인트

### Q. 왜 원문까지 저장했나요?

- 요약 품질 검증
- 요약 재생성 가능성
- 추후 검색/분류/재처리 확장성
- 외부 사이트 게시글 삭제 대비

### Q. 왜 테이블을 2개로 나눴나요?

- 원본 데이터와 파생 데이터를 분리하면 책임이 명확해짐
- summary 생성 정책을 바꿔도 원문 훼손 없음

### Q. 왜 Selenium이 아니라 BeautifulSoup인가요?

- 현재 사이트 구조가 서버 렌더링 HTML이라 파싱 가능
- 구현/운영 비용이 더 낮음
- Selenium은 필요할 때만 도입하는 것이 합리적

### Q. 왜 최근 1개월을 30일로 정의했나요?

- 비즈니스 규칙을 테스트 가능하게 고정하기 위해
- 경계값이 명확하고 운영 환경에서 예측 가능

### Q. 재실행하면 중복 저장되지 않나요?

- `source_url` 기준 upsert
- summary도 변경이 없으면 재생성 skip

### Q. 운영에서 가장 위험한 포인트는 뭔가요?

- 외부 사이트 HTML 구조 변경
- OpenAI 호출 실패
- 클라우드 서버 시간대 차이
- 배치 실패 시 알림/재시도 전략

## 16. 아직 남은 개선점

- sync 결과 로깅 강화
- summary 실패 시 재시도/부분 성공 정책 추가
- 공지 상세 API 또는 프론트 상세 연결
- 크롤링 파서의 HTML 구조 변경 감지 강화
- 운영 스케줄러 연동 문서 정리

## 17. 결론

이 기능은 “공지 게시판을 읽어서 그대로 보여주는 API”가 아니라,

- 크롤링
- 배치 동기화
- 데이터 보존 정책
- 구조화 요약
- 집계 API
- 운영 시간대/중복 비용 고려

까지 포함한 작은 데이터 파이프라인입니다.

면접에서는 이 점을 강조하는 것이 좋습니다.  
즉, “API 하나 만들었다”보다 “운영 가능한 공지 수집/요약 시스템을 설계하고 구현했다”라고 설명하는 편이 훨씬 강합니다.
