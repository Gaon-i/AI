# Chat Session Timeout Policy

## 개요

채팅 세션은 `chat_session` 테이블에 저장되며, 각 질문은 `chat_log`로 기록됩니다.  
현재 정책은 별도의 "대화 종료" 버튼 없이 `last_activity_at` 기준 비활성 시간을 계산해 세션 유효 여부를 판단합니다.

기본 설정값:

- `chat_session_timeout_minutes = 30`

즉, 마지막 질문 처리 시각으로부터 30분 이상 추가 질문이 없으면 해당 세션은 만료된 것으로 간주합니다.

## 왜 필요한가

채팅 세션 만료 정책은 단순히 오래된 세션을 막기 위한 기능이 아니라, 챗봇 운영 품질과 데이터 신뢰도를 유지하기 위한 기준입니다.

### 1. 대화 맥락 오염 방지

사용자가 앱을 오래 열어둔 뒤 다시 질문하면, 이전 대화와 현재 질문의 의도가 달라졌을 가능성이 큽니다.  
만료 없이 같은 `session_id`를 계속 재사용하면 서로 관련 없는 질문들이 하나의 대화로 묶이고, 이후 관리자 확인이나 대화 분석에서 실제 사용자 흐름을 파악하기 어려워집니다.

### 2. 로그와 통계의 기준 통일

`chat_session`은 한 번의 대화 단위를 나타내고, `chat_log`는 그 안에서 발생한 질문과 답변을 나타냅니다.  
세션 만료 기준이 없으면 하루 전 질문과 방금 질문이 같은 세션에 누적될 수 있어 `total_turns`, 사용자 활동 시각, 대화별 성공/실패율 같은 지표가 부정확해집니다.

### 3. 사용자 경험 명확화

오래된 화면에서 질문했을 때 서버가 조용히 이전 세션을 이어가면 사용자는 현재 대화가 새로 시작된 것인지, 예전 대화에 이어진 것인지 알기 어렵습니다.  
만료 에러를 명시적으로 반환하면 클라이언트는 새 세션을 만들고, 사용자에게 자연스럽게 새 대화를 시작하는 흐름을 제공할 수 있습니다.

### 4. 비정상 재사용과 불필요한 처리 방지

만료된 `session_id`가 계속 재사용되면 오래된 클라이언트 상태, 브라우저 캐시, 임의 요청이 실제 대화처럼 저장될 수 있습니다.  
만료된 세션에서는 새 `chat_log`를 만들지 않도록 제한하면 불필요한 DB 기록과 OpenAI 호출을 줄이고, 운영 중 추적해야 할 데이터도 깨끗하게 유지할 수 있습니다.

## 정책 상세

### 1. 세션 생성

- `POST /api/v1/ai/chat/sessions`
- 응답으로 `session_id`를 발급합니다.

### 2. 세션 사용

- `POST /api/v1/ai/chat`
- 요청 바디에 `session_id`를 반드시 포함해야 합니다.
- 서버는 `chat_session`을 조회한 뒤, 아래 순서로 검사합니다.

검사 순서:

1. `session_id`가 실제로 존재하는가
2. `last_activity_at`이 현재 시각 기준 30분 이내인가
3. 유효하면 `chat_log`를 `PROCESSING` 상태로 생성하고 답변 처리를 시작

### 3. 세션 만료

만료 조건:

- `datetime.utcnow() - last_activity_at > 30분`

만료된 세션에 대해서는:

- 새 `chat_log`를 만들지 않습니다.
- `chat_session.total_turns`를 증가시키지 않습니다.
- `chat_session.last_activity_at`를 갱신하지 않습니다.
- 클라이언트에 만료 에러를 반환합니다.

### 4. 재시작 방식

현재는 명시 종료 API가 없으므로, 만료된 세션은 재사용하지 않습니다.

클라이언트 처리 권장 흐름:

1. `/api/v1/ai/chat` 호출
2. `CHAT_SESSION_EXPIRED` 응답 수신
3. `/api/v1/ai/chat/sessions`로 새 세션 발급
4. 새 `session_id`로 질문 재전송

## 에러 코드

### `CHAT_SESSION_NOT_FOUND`

- HTTP Status: `404`
- 의미: 요청에 포함된 `session_id`가 DB에 존재하지 않음
- 예시 상황:
  - 잘못된 세션 ID 전달
  - 이미 다른 환경에서 사용하던 임의 값 전달

예시 응답:

```json
{
  "status": 404,
  "message": "chat session not found",
  "data": null,
  "error_code": "CHAT_SESSION_NOT_FOUND"
}
```

### `CHAT_SESSION_EXPIRED`

- HTTP Status: `409`
- 의미: 세션은 존재하지만 비활성 30분을 초과해 더 이상 사용할 수 없음
- 예시 상황:
  - 앱을 오래 켜두고 다시 질문한 경우
  - 이전 대화를 복구하려다 만료된 `session_id`를 재사용한 경우

예시 응답:

```json
{
  "status": 409,
  "message": "chat session expired after 30 minutes of inactivity. please start a new chat session",
  "data": null,
  "error_code": "CHAT_SESSION_EXPIRED"
}
```

## 로그를 남기는 이유

채팅 로그는 단순히 대화 내용을 저장하기 위한 테이블이 아닙니다.  
운영 중에는 "사용자가 무엇을 물었는지", "검색이 제대로 되었는지", "답변 생성이 어디서 실패했는지", "어떤 모델과 프롬프트 버전에서 문제가 생겼는지"를 추적해야 합니다.

따라서 `/api/v1/ai/chat`은 질문이 들어오면 먼저 `chat_log`를 만들고, 검색 결과는 `chat_retrieval_result`, 실패 원인은 `chat_error_log`에 나누어 남깁니다.  
이렇게 분리하면 답변 결과만 보는 것이 아니라, 답변이 만들어진 과정까지 확인할 수 있습니다.

### `chat_log`

`chat_log`는 질문 1건의 전체 처리 결과를 나타내는 중심 로그입니다.

| 필드 | 도움이 되는 지점 |
| --- | --- |
| `chat_log_id` | 질문 1건을 추적하는 기준 ID입니다. 관리자 상세 조회, 검색 결과, 에러 로그, 피드백을 연결할 때 사용합니다. |
| `session_id` | 같은 대화 안에서 발생한 질문들을 묶어 사용자의 대화 흐름을 확인할 수 있습니다. 세션 만료 정책이 제대로 작동하는지도 검증할 수 있습니다. |
| `user_id` | 특정 사용자의 반복 문의, 장애 제보, 악의적 사용 여부를 확인할 때 필요합니다. 비로그인 또는 익명 흐름에서는 `NULL`일 수 있습니다. |
| `question` | 사용자가 실제로 입력한 원문입니다. 답변 품질 검수, FAQ 후보 발굴, 질문 패턴 분석에 사용합니다. |
| `rewritten_query` | 검증 또는 정규화 이후 검색에 사용한 질문입니다. 원문과 검색 질의가 다를 때 검색 품질 문제를 분석하는 기준이 됩니다. |
| `answer` | 사용자에게 반환된 최종 답변입니다. 관리자 검수, 사용자 피드백 대응, 잘못된 답변 재현에 사용합니다. |
| `answer_status` | `PROCESSING`, `SUCCESS`, `NO_ANSWER`, `ERROR` 상태로 처리 결과를 구분합니다. 실패율, 미답변율, 처리 중 멈춘 요청을 모니터링하는 핵심 지표입니다. |
| `model_name` | 어떤 답변 모델이 사용되었는지 남깁니다. 모델 변경 후 답변 품질이나 비용, 지연 시간이 달라졌는지 비교할 때 필요합니다. |
| `prompt_version` | 어떤 프롬프트 버전으로 답변했는지 남깁니다. 프롬프트 개선 전후의 성공률, 오답률, citation 품질을 비교할 수 있습니다. |
| `retrieval_version` | 어떤 검색 전략으로 chunk를 가져왔는지 남깁니다. 검색 로직 변경 후 품질 차이를 분석할 수 있습니다. |
| `response_time` | 질문 처리에 걸린 전체 시간입니다. 성능 저하, 외부 API 지연, 부하 테스트 결과를 판단하는 기준입니다. |
| `created_at` | 질문 발생 시각입니다. 시간대별 사용량, 장애 발생 시간대, 특정 배포 이후 문제 발생 여부를 확인할 수 있습니다. |

### `chat_retrieval_result`

`chat_retrieval_result`는 답변 생성 전에 어떤 문서 chunk가 검색되었는지 기록합니다.  
챗봇 답변 품질은 대부분 "검색이 맞았는가"와 "검색 결과를 모델이 잘 사용했는가"로 나뉘기 때문에, 이 로그가 있어야 원인을 분리할 수 있습니다.

| 필드 | 도움이 되는 지점 |
| --- | --- |
| `chat_log_id` | 어떤 질문에서 나온 검색 결과인지 연결합니다. 답변이 이상할 때 해당 질문의 검색 근거를 바로 확인할 수 있습니다. |
| `regulation_chunk_id` | 실제 검색된 규정 chunk를 가리킵니다. 잘못 검색된 문서인지, chunk 자체가 부정확한지 확인할 수 있습니다. |
| `document_id` | 어떤 규정 문서에서 검색 결과가 나왔는지 확인합니다. 특정 문서가 과도하게 검색되거나 누락되는 문제를 찾을 수 있습니다. |
| `document_version` | 검색 당시 사용된 문서 버전입니다. 문서 개정 이후에도 과거 답변이 어떤 버전을 근거로 했는지 추적할 수 있습니다. |
| `chunk_id` | 문서 안의 구체적인 chunk를 식별합니다. chunk 분할 품질이나 중복 chunk 문제를 확인할 때 사용합니다. |
| `retrieval_rank` | 검색 결과 순위입니다. 정답 근거가 상위에 있었는지, 낮은 순위라 모델이 놓쳤는지 판단할 수 있습니다. |
| `retrieval_score` | 벡터 검색 유사도 점수입니다. 유사도가 낮은 검색 결과로 답변한 경우 검색 품질 개선이 필요한 신호가 됩니다. |
| `rerank_score` | 향후 rerank를 도입할 때 1차 검색 점수와 재정렬 점수를 비교하는 기준입니다. 현재 값이 비어 있어도 확장 포인트로 남겨둡니다. |
| `retrieval_method` | 단일 생활관 검색인지, 생활관별 그룹 검색인지 같은 검색 방식을 남깁니다. 검색 전략별 성능과 품질 비교에 사용합니다. |
| `used_in_answer` | 검색 결과가 최종 답변에 사용되었는지 표시합니다. 검색은 되었지만 답변에서 무시된 근거를 확인할 수 있습니다. |
| `selected_as_citation` | 답변 citation으로 실제 선택된 chunk인지 표시합니다. citation 정확도와 근거 표기 품질을 검수할 때 필요합니다. |
| `citation_order` | 답변에서 몇 번째 근거로 사용되었는지 나타냅니다. `[C1]`, `[C2]` 같은 표시와 실제 chunk를 연결할 수 있습니다. |
| `created_at` | 검색 결과가 저장된 시각입니다. 특정 시점의 검색 로직 변경이나 장애와 연결해 분석할 수 있습니다. |

### `chat_error_log`

`chat_error_log`는 실패한 질문의 원인을 별도로 저장합니다.  
`chat_log.answer_status = ERROR`만으로는 어디서 왜 실패했는지 알 수 없기 때문에, 에러 유형과 발생 단계를 분리해 남깁니다.

| 필드 | 도움이 되는 지점 |
| --- | --- |
| `error_id` | 에러 로그 1건을 식별합니다. 동일 질문에서 여러 에러가 쌓일 가능성에 대비한 기준 ID입니다. |
| `chat_log_id` | 실패한 질문과 에러를 연결합니다. 관리자 화면에서 질문, 답변 상태, 에러 원인을 함께 볼 수 있습니다. |
| `session_id` | 같은 대화 안에서 반복적으로 실패하는지 확인할 수 있습니다. 특정 세션의 상태 이상을 추적할 때 필요합니다. |
| `error_type` | `TIMEOUT`, `LLM_API_ERROR`, `RETRIEVAL_ERROR`, `VALIDATION_ERROR`처럼 실패 성격을 구분합니다. 장애 집계와 우선순위 판단에 사용합니다. |
| `occurred_step` | `QUESTION_VALIDATION`, `RETRIEVAL`, `ANSWER_GENERATION`, `RESPONSE_RENDERING` 등 실패 지점을 남깁니다. 어느 단계가 병목인지 바로 파악할 수 있습니다. |
| `error_message` | 사람이 빠르게 읽을 수 있는 에러 요약입니다. 운영자가 장애 상황을 1차로 판단하는 데 사용합니다. |
| `error_detail` | 예외 타입과 상세 메시지입니다. 재현, 디버깅, 외부 API 오류 분석에 사용합니다. |
| `created_at` | 에러 발생 시각입니다. 배포 시점, 외부 API 장애 시간, 트래픽 증가 시간과 비교할 수 있습니다. |

## 예상 질문과 답변

### Q1. 왜 세션 만료 시간이 30분인가요?

30분은 일반적인 사용자 이탈과 일시 중단을 구분하기 위한 기본값입니다.  
잠깐 앱을 벗어났다가 돌아오는 사용자는 같은 대화를 이어갈 수 있고, 오래 방치된 화면에서 다시 질문하는 경우는 새 대화로 분리할 수 있습니다.

### Q2. 사용자가 30분 후에 이어서 질문하고 싶으면 어떻게 하나요?

현재 정책에서는 만료된 `session_id`를 재사용하지 않습니다.  
클라이언트는 `CHAT_SESSION_EXPIRED` 응답을 받으면 새 세션을 발급한 뒤 같은 질문을 다시 보내야 합니다.

### Q3. 만료된 세션에 질문이 들어왔을 때 새 `chat_log`를 만들지 않는 이유는 무엇인가요?

만료된 세션에 새 로그를 만들면 실제로는 새 대화에 가까운 질문이 이전 대화에 섞입니다.  
이렇게 되면 `total_turns`, 최근 활동 시각, 대화별 성공/실패 분석이 부정확해지므로 만료된 세션에서는 질문 로그를 남기지 않습니다.

### Q4. 세션을 자동으로 새로 만들면 더 편하지 않나요?

서버가 자동으로 새 세션을 만들 수도 있지만, 현재는 클라이언트가 명시적으로 새 세션을 발급받는 방식을 사용합니다.  
이 방식은 클라이언트가 만료 상태를 인지하고 UI를 갱신할 수 있어, 사용자가 새 대화로 전환되었다는 흐름을 더 명확하게 만들 수 있습니다.

### Q5. 왜 HTTP 409를 사용하나요?

`session_id` 자체는 존재하지만 현재 상태에서는 더 이상 사용할 수 없기 때문입니다.  
존재하지 않는 세션은 `404`, 존재하지만 만료되어 요청을 처리할 수 없는 세션은 `409`로 구분합니다.

### Q6. 세션 만료가 답변 생성 중에도 발생할 수 있나요?

현재 만료 검사는 `/api/v1/ai/chat` 요청을 받는 시점에 수행합니다.  
검사를 통과하면 해당 질문에 대한 답변 처리는 계속 진행되며, 처리 도중 30분 기준을 넘었다는 이유만으로 중단하지 않습니다.

### Q7. 사용자가 계속 질문하면 세션 만료 시간이 연장되나요?

네. 유효한 세션으로 질문이 들어오면 `last_activity_at`이 갱신됩니다.  
따라서 사용자가 계속 대화하고 있는 동안에는 마지막 활동 시각 기준으로 만료 시간이 다시 계산됩니다.

### Q8. 30분 기준은 나중에 바꿀 수 있나요?

네. `chat_session_timeout_minutes` 설정값으로 관리하므로 코드 흐름을 바꾸지 않고 환경 설정으로 조정할 수 있습니다.  
운영 데이터에서 사용자가 자주 만료를 겪는다면 45분이나 60분으로 늘릴 수 있고, 불필요한 세션 유지가 많다면 더 짧게 줄일 수 있습니다.

### Q9. 명시적인 대화 종료 버튼이 없는 이유는 무엇인가요?

현재 정책은 사용자가 별도 종료 행동을 하지 않아도 비활성 시간만으로 세션을 정리하는 방식입니다.  
초기 구현에서는 클라이언트 UI를 단순하게 유지하고, 서버가 일관된 기준으로 세션 유효성을 판단하도록 하는 것이 목적입니다.

### Q10. 만료된 세션 데이터는 삭제되나요?

아니요. 이 정책은 세션을 삭제하는 정책이 아니라, 더 이상 새 질문에 사용할 수 없도록 판단하는 정책입니다.  
기존 `chat_session`과 `chat_log`는 관리자 확인, 장애 분석, 통계 집계를 위해 유지됩니다.

## 수동 테스트 시나리오

### 정상 흐름

1. `POST /api/v1/ai/chat/sessions` 호출
2. 받은 `session_id`로 즉시 `POST /api/v1/ai/chat` 호출
3. `SUCCESS` 또는 `NO_ANSWER` 응답 확인

### 존재하지 않는 세션

1. 임의의 `session_id`로 `POST /api/v1/ai/chat` 호출
2. `404`, `CHAT_SESSION_NOT_FOUND` 응답 확인

### 만료된 세션

1. 세션 생성 후 `last_activity_at`를 강제로 30분 이전으로 조정
2. 해당 `session_id`로 `POST /api/v1/ai/chat` 호출
3. `409`, `CHAT_SESSION_EXPIRED` 응답 확인
