# 공지사항 운영서버 배치 가이드

## 1. 목적

이 문서는 운영 서버에서 학생생활관 공지사항 수집 배치를 매일 12시에 안정적으로 실행하기 위한 기준을 정리한 문서입니다.

대상 기능:
- `python -m app.jobs.notice_sync`
- 최근 30일 공지 수집
- 원문 저장
- 요약 생성
- 30일 초과 공지 삭제

## 2. 운영 구조 요약

운영 구조는 아래처럼 가져갑니다.

1. 애플리케이션 코드는 배치 커맨드만 제공
2. 운영 서버의 외부 스케줄러가 배치 커맨드를 매일 호출
3. 배치는 실행할 때마다 최신 공지와 DB 상태를 동기화

즉, 애플리케이션 내부에 상시 스케줄러를 두는 것이 아니라 서버가 정해진 시간에 배치 커맨드를 실행하는 구조입니다.

## 3. 사전 준비

운영 서버에는 아래가 준비되어 있어야 합니다.

- Python 3.9 이상
- 프로젝트 코드 배포 경로
- 가상환경 `.venv`
- PostgreSQL 또는 RDS 연결 정보
- OpenAI API Key
- 서버 시간대 설정 또는 실행 시각 기준 확인

## 4. 필수 환경변수

운영 서버에서는 최소 아래 값이 필요합니다.

```env
APP_ENV=prod
APP_NAME=gaon-i-ai
DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DB_NAME
OPENAI_API_KEY=sk-...
```

추가로 운영 정책상 필요하면 아래도 함께 설정합니다.

```env
API_V1_PREFIX=/api/v1
OPENAI_TIMEOUT_SECONDS=10.0
```

## 5. 배포 후 최초 1회 체크리스트

1. 저장소 최신 코드 배포
2. 가상환경 의존성 설치
3. Alembic migration 적용
4. 운영 환경변수 반영
5. 배치 수동 실행
6. DB 적재 결과 확인
7. API 응답 확인

## 6. 운영 서버 수동 실행 절차

```bash
cd /path/to/Gaon-i
source .venv/bin/activate
alembic upgrade head
python -m app.jobs.notice_sync
```

정상 실행 시 출력 예시는 아래와 같습니다.

```json
{"crawled_count":1,"saved_count":1,"summarized_count":1,"deleted_count":0}
```

## 7. 배치 실행 방식

### 권장 원칙

- 스케줄링은 운영 서버가 맡는다.
- 애플리케이션은 실행 가능한 배치 커맨드만 제공한다.
- 실패 여부는 운영 로그와 알림에서 관리한다.

### cron 예시

매일 12:00 KST 실행:

```bash
0 12 * * * cd /path/to/Gaon-i && /path/to/Gaon-i/.venv/bin/python -m app.jobs.notice_sync >> /var/log/gaon-i-notice-sync.log 2>&1
```

### systemd timer 예시

운영 서버에서 좀 더 구조적으로 관리하고 싶으면 `systemd service + timer` 조합도 가능합니다.

서비스 예시:

```ini
[Unit]
Description=Gaon-i notice sync job

[Service]
Type=oneshot
WorkingDirectory=/path/to/Gaon-i
ExecStart=/path/to/Gaon-i/.venv/bin/python -m app.jobs.notice_sync
Environment=APP_ENV=prod
```

타이머 예시:

```ini
[Unit]
Description=Run Gaon-i notice sync daily at 12:00

[Timer]
OnCalendar=*-*-* 12:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

## 8. 시간대 기준

현재 코드 기준 운영 시간은 KST를 기준으로 맞추는 것이 권장됩니다.

이유:
- 공지 등록일과 운영 확인 기준이 한국 시간 기준임
- "이번 주", "이번 달", "최근 30일" 해석이 운영자 기대와 맞아야 함

운영 서버가 UTC로 설정되어 있어도 배치 실행 시간은 KST 기준으로 맞춰야 합니다.

## 9. 데이터 수명주기

배치가 돌 때마다 아래 규칙을 적용합니다.

- 최근 30일 이내 공지: 유지
- 신규 공지: 저장 + 요약 생성
- 기존 공지:
  - 내용 변경 없음: 재요약 skip 가능
  - 내용 변경 있음: 재요약
- 30일 초과 공지: `notice_summary` 먼저 삭제 후 `notice` 삭제

## 10. 운영 검증 포인트

배치 실행 후 아래를 확인합니다.

### DB 확인

- `notice` 테이블 적재 수
- `notice_summary` 적재 수
- `posted_at` 기준 최근 30일 데이터만 남았는지
- `source_url` 중복이 없는지

### API 확인

- `GET /api/v1/notices`
- `weekly_count`
- `monthly_count`
- 공지 목록 DTO 정상 여부

## 11. 장애 대응 체크포인트

### 1. 외부 사이트 크롤링 실패

가능 원인:
- 학교 사이트 구조 변경
- 네트워크/DNS 문제
- 302/인코딩 경로 변경

확인 방법:
- 운영 서버에서 공지 목록 URL 직접 접속
- 배치 로그 확인
- HTML 구조 변경 여부 확인

### 2. OpenAI 요약 실패

가능 원인:
- API Key 누락
- 호출 제한
- 네트워크 문제
- 응답 포맷 불일치

확인 방법:
- `OPENAI_API_KEY` 설정 확인
- 배치 stderr 로그 확인
- 수동으로 단건 요약 API 호출 확인

### 3. DB 적재 실패

가능 원인:
- RDS 연결 실패
- migration 미적용
- schema mismatch

확인 방법:
- `alembic current`
- DB 연결 테스트
- `notice`, `notice_summary` 테이블 존재 여부 확인

## 12. 운영에서 추천하는 추가 보강

현재 구현 위에 아래를 더 얹으면 운영 안정성이 높아집니다.

- 배치 실행 로그를 파일/로그 수집기로 적재
- 실패 시 Slack 또는 Discord 알림
- 요약 실패 공지 재처리용 별도 재시도 배치
- 크롤링 결과 개수 이상치 감지
  - 예: 평소 5건인데 갑자기 0건
- 마지막 성공 실행 시각 저장

## 13. 면접 또는 인수인계 때 한 줄 설명

"운영에서는 앱 내부에 스케줄러를 넣지 않고, `python -m app.jobs.notice_sync` 배치 커맨드를 외부 스케줄러가 매일 12시에 호출하도록 설계했습니다. 이렇게 하면 배포와 장애 대응이 단순해지고, 서버가 여러 대일 때도 스케줄링 책임을 분리해서 관리할 수 있습니다."
